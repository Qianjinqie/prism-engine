## ⚠️ v2.1 单文件分发包含已知 BSDF 多散射补偿缺陷（v2.2 已修）

**受影响产物**：`dist/prism-engine-v2.1-source.txt`（打包于 2026-10-27，早于修复提交
`5b8ded4`，**包含此缺陷**）。

**缺陷描述**：`prism-rt` 的 Disney BSDF 多散射能量补偿采用错误的「逐通道各自 F0 查表回填」形式
（`ms_ch = (1−E_o)(1−E_i)·f0_ch / (π(1−E_avg))`，`E` 取自 `energy_dir(·,·,f0_ch)`）。
低 F0 通道的 `(1−E)` 更大、`1−E_avg` 更小，相除把回填量在 `f0→0` 侧放大，补偿幅度不随 F0 单调。
表现为高饱和金属（金、铜）在低粗糙度、掠射角下蓝绿通道被过量补能，整球偏成补色（金球发青绿）。

> **注意**：`energy_dir` / `energy_avg` 出口的 `clamp(0,1)` 防御**不是**本次缺陷的主因——
> 该 clamp 在当前能量 LUT 上**零触发**（金/铜/银在 α∈[0.05,0.35]、μ∈[0.05,0.25] 全域
> raw 值均 < 1）。主因是补偿形式由「逐通道 F0 查表回填」置换为 Fdez-Agüera 2019 彩色导体形式。

**实测影响量级**（金 f0=1.000/0.766/0.336，α=0.05、μo=0.25、μi=0.25）：
- R 通道旧→新比值 **1.000**（f0=1 处新旧重合）；
- G 通道旧/新 = **3.85×**；B 通道旧/新 = **18.92×**；
- 极端掠射（μo=0.1、μi=0.8）B 通道达 **49.83×**。

**v2.2 修复**：改为 Fdez-Agüera 2019 彩色导体形式——幅度取白炉表（F0=1），色相由半球平均
Fresnel `F_avg = f0 + (1−f0)/21` 承担。详见 `CHANGELOG.md` 的 **R-2026-xx-05**（四要素已登记，
含逐通道旧→新比值与 clamp 非主因说明）。

**建议**：使用 v2.1 单文件分发渲染高饱和金属、且关注掠射角补色一致性的用户，请升级至 v2.2；
或回退到修复提交 `5b8ded4` 之后的源码树重新打包（不单独发 v2.1.1）。

#### 根因（作者判断成立：**V1.0 的测试本身写错了**）

`gi_prim_dist` 球分支返回 `q.x`，只与 x 有关——是**沿 x 的无限大板**。射线沿 y/z 前进时
该「距离」不随 t 变化（梯度恒为 0），`t += d·safety` 给出恒定步长，能否在 `max_steps=48`
步内跨过 `t_max=20` 取决于浮点舍入累积——**数值病态**。

决定性对照（同一份源码、两种 GPU）：

| 源码 | wasm | 环境 | `gpu.gi_compute` |
|---|---|---|---|
| 修复前 | 432,052 B | SwiftShader 软件适配器 | **PASS**（17/17） |
| 修复前（同一份） | 432,052 B | **真机** Android / 真 GPU | **FAIL**，整块零值 |
| 修复后 | 439,539 B | SwiftShader | **PASS**（18/18） |

> 表内 `17/17` / `18/18` 是**当轮 harness 项数**的快照（`gpu.params_roundtrip`、`gpu.gi_layout`
> 是后续分两次加入的）。**最终版为 19 项、SwiftShader 19/19**，勿把本表的 18/18 读成当前值。

软件适配器的浮点行为接近 CPU，两端「同错得一致」→ 判据恒绿；真 GPU 的 FMA 收缩不同
→ 整体翻到「全遮挡」一侧。**V1.0 那次全 PASS 是碰巧落在与 CPU 同一侧，不是验对了。**

#### 修复

1. 球 SDF：`q.x` → `length(p-c) - r`（CPU 与 WGSL **同步**）
2. 容量填充 `GI_PRIMS[2..4]`：`原点+r=1` → `radius 0 + center(0,-1e6,0)`（即使 `prim_count` 被误读成 4 也绝不命中）
3. 越界守卫：四个入口的计数上界全部 clamp 到编译期容量 / `arrayLength`
4. 新增 `gpu.params_roundtrip`：`GiParams` 256 B 写 uniform 再读回，逐字节 + 4 个关键字段解释值
5. 哨兵：`samples`=-1 / `sh`=-2 / `irradiance`=-3，FAIL 时可三分「入口没执行 / 全遮挡 / 可见」
6. `WASM_URL` 加内容指纹（`?v=<sha256 前 8 位>`）—— 此前无版本参数，浏览器强缓存会让「改了但测不出来」成立

#### 方法论结论

> **「CPU 参考 vs GPU 镜像」的自洽对拍，只有在两端算法本身正确时才有判别力。**
> 两端同错时它恒绿，且软件适配器（SwiftShader）与 CPU 浮点行为接近，**永远无法暴露**——只有真硬件 GPU 能。
> 推论：判据建立在「两端一致」上的测试项，**必须至少有一条真机证据**。

#### 责任边界：按规范输出的缺陷归因于驱动，但不豁免可用性

> 若某设备 FAIL，先走三步判别：① 同一份 wasm 在 SwiftShader 上是否 PASS →
> ② 布局 census / 字节 dump 是否与规范一致 → ③ 是否仅特定设备 FAIL 且换兼容面更大的写法即 PASS。
> 三步全过，方可归因驱动偏离规范，**不计为本项目缺陷**。
>
> **但这条只在三种举证齐备时成立**：输出可证符合规范（逐字节 dump + 布局自检）、
> 规范实现上通过、已尽合理规避（选规范交集写法，不踩灰区）。
> 且**不豁免可用性责任**——驱动导致的不可用仍须登记兼容项并给降级路径
> （`cpu_fallback` / 适配器能力判定），**不得以"符合规范"关闭问题单**。
