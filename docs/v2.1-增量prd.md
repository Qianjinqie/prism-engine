### 3.1 流 A（重）：#11 GPU 渲染管线

#### A1（P0）Vulkan `render_scene` 光线追踪管线真实化

- **现状**：`CpuRefBackend`（`prism-gpu/src/lib.rs:411-508`）软件光追可出图；Vulkan 侧 compute dispatch 真实（lavapipe 256 元素对拍 ULP=0）、SPIR-V 发射/校验/反汇编就绪（`vulkan/spirv.rs`）、background kernel 首帧真实（三尺寸逐字节 0 差异）；但 `VulkanBackend::render_scene` 恒返回 `Framebuffer::empty()`（`vulkan/mod.rs:822`），调用方回退 CPU——光追场景管线未实现。
- **V2.1 目标**：以 compute 路径实现光追渲染 kernel（与 `CpuRefBackend` 同构算法：球体相交 + 直接光 + aesthetic 后处理；注意 CPU 参考的 `filmic` 为 Reinhard（`lib.rs:497-500`），**不经 ACES 矩阵**），经既有 SPIR-V 发射 → dispatch → fence → readback 闭环，使 `render_scene` 在 lavapipe 实机产出有效帧。
- **验收判据**：
  1. **实机出图**：有 Vulkan 设备（lavapipe ICD 在位）时，`render_scene` 返回 `is_valid()` 帧（`width×height×4` 字节），与 `CpuRefBackend` 对同一 `SceneRenderRequest` 对拍。对拍判据分两层：① **GPU 自跑双次逐位一致**（G3，硬判据）；② **GPU vs CPU 参考统计 diff**（`max_channel_delta` / differing_pixels 比例），阈值定义见 **Q1**（C15 跨后端只承诺视觉等价，无数值；compute 先例为 ULP=0，光追含 sqrt/除法/归一化，预期有 ULP 差，故取统计判据）。
  2. **无设备诚实分支**：CI/沙箱无 GPU 时，测试以运行期自门控覆盖（有设备真断言、无设备如实报 skip 分支，既有先例 `vulkan/compute.rs:1271-1282`、`loader.rs:889`），**禁止 `#[ignore]`**；且无设备时 `is_available()` 断言为 false。
  3. **可用性语义闭合**：不允许出现「`is_available()==true` 但 `render_scene` 出空帧」的组合。语义升级方案（compute 自检 → compute+render 双自检，或新增独立 render 自检 API）见 **Q4**；无论取哪案，既有测试 `availability_requires_verified_dispatch_not_just_a_device` 须同步更新且更新后全绿。
  4. **边界形态**：沿用 background kernel 三尺寸先例（整除快路径 / 带尾组守卫 / 极端或负参数）扩展到 render 路径；`u32::MAX×u32::MAX` 等极端尺寸秒回不 panic（既有 G6/G7/G10 守卫语义保持）。
  5. G1–G6 全局判据全满足。
- **依赖**：A0 既有资产（compute dispatch + SPIR-V 发射器 + background kernel）；与 C3（T4）**无耦合**——`SceneRenderRequest` 的 aesthetic 口径（Reinhard filmic）不消费 ACES 矩阵，对拍基准不随 T4 移动（见风险 R2）；Q1/Q4 的决策须在开工前落定。

#### A2（P1）Metal render 代码同构实现 + 编译门控（不点亮）

- **现状**：Metal 后端（`metal/mod.rs`，764 行）探测链仅 macOS 编译（`loader` 模块 `#[cfg(target_os="macos")]`），MSL「双份源」注册表全平台可见，1 个真实样例 kernel；`render_scene` 返回无效空帧，`is_available()` 恒 false（「探测到设备 ≠ 能出图」的宪章式诚实）。Linux 沙箱无 macOS 工具链与 Metal 运行时，**无法实机验证**。
- **V2.1 目标**：按 A1 的 kernel 设计同构编写 Metal render 管线代码（MSL 双份源补齐 + render 路径），**不点亮 `is_available()`**；以编译门控 + 文案纪律保证诚实口径。
- **验收判据**：
  1. Linux 上 `cargo xtest` 编译通过（metal 模块全平台参与编译的现状保持，不得被 cfg 排除出构建）。
  2. `MetalBackend::is_available()` 在所有平台恒 false，既有钉子测试（`metal_stub_render_scene_returns_invalid_frame_without_panic`）保持绿；非 macOS 上 `render_scene` 仍返回无效帧，**不得产出假帧**。
  3. macOS-only 的 render 实现代码存在，且模块文档如实标注「未实机验证」；全仓（代码注释 + 文档 + 交付说明）无任何一处声称 Metal 可用；「探测链就绪」与「真实 dispatch」分述（G4）。
  4. QA 文案审查专检项：交付说明中 Metal 条目必须含「未点亮 / 未实机验证」字样。
  5. G1–G6 全局判据全满足。
- **依赖**：A1 的 kernel 设计结论（同构移植）；macOS 实机验证**不在 V2.1 验收范围**（沙箱无工具链），在交付说明中显式留名（见 Q5）。

#### A3（P2）WebGPU 渲染路径可行性评估结论

- **现状**：WebGPU 路径 7,655 行，浏览器绑定厚实，wasm/移动测试链在用；但仅 scan/sort compute 内核，**无渲染路径**；非 wasm 目标 `render_scene` 走 CPU 兜底（`web/device.rs:169-172`）。
- **V2.1 目标**：产出书面可行性评估结论（落盘 `docs/`），回答：WebGPU render 路径（WGSL 光追 kernel + 浏览器实机验证链路）可行性、工作量量级、与 A1 管线的共享边界（SPIR-V 发射器 vs WGSL 手写）、以及 §10.3 的岔路决策建议（自研补完 vs wgpu）。
- **验收判据**：
  1. 评估文档落盘，结论明确（可行 / 条件可行 / 不可行），含量级估计、依赖分析、决策建议；**不做实现**。
  2. 文档如实区分「已有绑定/测试链」与「未建渲染路径」，不得把绑定厚度表述为渲染能力（G4 同款纪律）。
  3. G1–G6 全局判据全满足。
- **依赖**：A1 的管线设计结论（kernel 结构是否可移植到 WGSL）。
