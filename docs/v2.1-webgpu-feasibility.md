# V2.1 A3：WebGPU 渲染路径可行性评估

> 归属：V2.1 流 A / T-A3（P2）｜作者：工程师（GPU 流 A）
> 输入：`docs/v2.1-增量prd.md` §3.1 A3、`docs/v2.1-增量设计.md` §1.1 A3
> 范围：**只出结论，不实现**（PRD §4 非目标：WebGPU 渲染路径实现）
> 纪律：本文件严格区分「已有绑定/测试链」与「已建渲染能力」（G4 同款口径）；
> 所引现状均有 `文件:行号` 可查。

## 0. 结论（TL;DR）

**条件可行（Conditionally Feasible）**：技术路径成立，工作量天级（**4–6 人日**，
估算），与既有 WebGPU 绑定层高度复用；但**验收链不可在 CI 沙箱内自动化**——
必须回到 D-14 的「浏览器 + 真机」人工链路，这是主要成本与主要风险。
V2.1 **不做实现**（PRD 非目标）；建议作为 V2.2 的独立任务排期，前置条件是
先有 A1 的 Vulkan 参考实现（**已具备**）。

| 维度 | 判定 | 依据 |
|---|---|---|
| 技术可行性 | ✅ 成立 | 算法与 A1 完全同构（逐像素独立算子）；WGSL 有 compute + storage buffer，足以表达 4 绑定 megakernel（`web/mod.rs:76-138` 的胶水已支持 bind group + dispatch） |
| 工程可复用度 | ✅ 高 | 14 个 JS 胶水函数、句柄表、两阶段 `run`/`collect` ABI、浏览器 harness 全部**已在用**（`web/abi.rs`、`web/index.html`） |
| 工作量 | 🟡 天级 | 4–6 人日（§2 拆解：WGSL 1–2 + 接线 1 + 真机验证 2–3） |
| 验收可自动化 | ❌ 不能 | 无浏览器运行时；native 下全部 GPU 胶水桩返回 0（`web/abi.rs:31-35`），只能 `Skip` |
| 零依赖约束 | ✅ 可守 | 不引 wgpu/wasm-bindgen；沿用现有手写 `extern "C"` 胶水路线 |
| 确定性承诺 | 🟡 降级 | 浏览器/驱动差异下只能承诺「同设备双跑逐字节一致 + 跨后端统计等价」，不能承诺逐字节跨设备 |

**一句话**：**能写，且写起来不贵；但「证明它写对了」比「写」贵**——这是它与
A1（Vulkan，可在 CI 内用 lavapipe 全自动验证）最本质的差别。

## 1. 现状勘定（三类，禁止混淆）

### 1.1 已有且**在用**（绑定 + 测试链）

| 项 | 证据 | 说明 |
|---|---|---|
| 手写浏览器绑定 | `web/mod.rs:36-139` | **14 个** `extern "C"` 导入函数（4 能力探测 + 9 资源创建/执行 + 1 错误上报），零 `wasm-bindgen` |
| JS 胶水 + 句柄表 | `web/index.html:414-433` 等 | 宿主侧 `Map<u32, GPUObject>`；`prism_create_bind_group` 支持 `@group(g)` 索引 |
| 两阶段 ABI | `web/abi.rs:1-35` | `run` 提交 → `Pending` → 宿主 `await` → `collect` 读回（WASM 同步栈无法 await 的规避） |
| 真实 WGSL compute 内核 | `web/device.rs:181+` | scan（Blelloch 上扫）与 histogram/sort 的 WGSL 源，经 ABI 测试项在 Android/桌面 Chrome 真机跑过（D-14） |
| 16 份 WGSL 源 + 结构自检 | `shaders/`（16 文件）、`shaders.rs:519-700` | 三目标（WGSL/MSL/SPIR-V）宿主表交叉锚定；结构自检（入口/括号/禁 libm/未解析符号） |
| native 桩 | `web/mod.rs:176-180` | 非 wasm 目标返回 `NotWasmTarget`，需 GPU 的测试项 `Skip`，不影响 `cargo test` |

**这段厚度说明的是「绑定与测试链成熟」，不是「能渲染」。**

### 1.2 已存在但**未接线**

* `shaders/rt_scene.wgsl`（269 行）、`rt_shade.wgsl`、`rt_wavefront*.wgsl`、
  `rt_bvh.wgsl`：这些是 **prism-rt 的场景访问/wavefront 逻辑源**（判对基准是
  `crates/prism-rt/src/{integrator,bsdf,light,bvh}.rs`），用途是「真机编译 +
  结构自检」，**没有任何一条被接到 render pass / compute 提交上**。
* `shaders.rs` 的三目标宿主表：登记了 WGSL/MSL/SPIR-V 三种形态，但**不产生
  任何 dispatch**。

### 1.3 **未建**（这就是缺口本体）

* **没有渲染 kernel**：`WebGpuBackend::render_scene`（`web/device.rs:169-174`）
  恒走 `CpuRefBackend`——不是「降级」，是**唯一路径**。
* **没有图像输出路径**：`web/abi.rs` 的读回只覆盖 storage buffer → 线性内存，
  没有「帧缓冲 → RGBA8 字节」的渲染专用封装（其实不需要，storage buffer 足够，
  见 §2.2）。
* **没有渲染对拍测试**：现有 harness 测试项里没有 `render_scene` 项。

## 2. 迁移量拆解（估算，按 A1 已交付的 Vulkan 实现外推）

### 2.1 WGSL megakernel（手写第 4 份源）：~260 行，1–2 人日

* **不移植 SPIR-V 发射器**：`vulkan/spirv_rt.rs` 是「WGSL 子集 → SPIR-V 二进制」
  的自研发射器；WGSL 本身是**文本输入**，没有「文本→文本」的稳定规范可依
  （与 MSL 同一定案，见 `metal/msl/mod.rs:6-12`）。故走**手写双份源**：
  `shaders/scene_frame.wgsl`（新），入口 `scene_main`，与 MSL/SPIR-V 同名同工作组。
* **布局差异（唯一实质技术点）**：WGSL 的 `array<f32>` + 手动索引与 Vulkan 侧
  扁平槽位一一对应（球 8 槽 / 灯 8 槽），**不引入 std430 结构体对齐问题**
  ——这恰好是 A1 已验证过的布局（`vulkan/spirv_rt.rs` 的 `SPHERE_SLOTS/LIGHT_SLOTS`）。
  参数块的 f32 位型传参在 WGSL 用 `bitcast<f32>(u)`，语义与 SPIR-V 的
  `OpBitcast` 完全一致。
* **控制流更简单**：WGSL 的 `for` 循环直接可用（不像 SPIR-V 要手工构造
  `OpLoopMerge` + `Function` 局部变量）；代码量比发射器少一个数量级。
* 可直接照抄的语义件：求交公式、`scene_normalize` 的 `1e-8` 退化守卫、
  `floor(x*255 + 0.5)` 量化、`r | g<<8 | b<<16 | 255<<24` 打包（与
  `CpuRefBackend::render_scene` 逐式对应，A1 已在真机证明该写法与 CPU 逐字节一致）。

### 2.2 宿主管线接线：~80 行 Rust + ~0 行新 JS，1 人日

* 四个 storage buffer（params/spheres/lights/out）→ 现有
  `prism_create_buffer` / `prism_write_buffer` / `prism_create_bind_group` /
  `prism_dispatch` 全部够用（`web/mod.rs:76-138`）。**绑定集是连续前缀
  `{0,1,2,3}`**，正好满足现有「每个 group 的绑定从 0 起连续」的强制约定
  （`web/mod.rs:100-114` 的注释）。
* 沿用「4 绑定 + 8×8 工作组 + ceil(w/8)×ceil(h/8)」的 dispatch 形状，与
  Vulkan/MSL 同形（便于三端对拍）。
* 唯一需要新增的胶水：**无**。读回走既有 `prism_read_buffer` + `prism_copy_out`。

### 2.3 浏览器实机验证链：2–3 人日（含人工真机）

* 在 `web/abi.rs` 的测试项清单里新增 1 项（`run` 提交 → `Pending` → `collect`
  比对），判据沿用 A1 的两层：**同设备双跑逐字节一致**（硬）+ **vs CPU 统计
  等价**（软，阈值可复用 A1 收窄后的 ≤1/255）。
* 需要在 Android Chrome / 桌面 Chrome 上各跑一次并留档（D-14 既有链路）。
* **这是唯一不可自动化的一块**：本地沙箱无浏览器 GPU 运行时。

> **合计：4–6 人日**（不含浏览器兼容性返工）。对比 A1 的 Vulkan 周级，量级明显更小——
> 因为「算法 + 判据 + 布局」都已由 A1 定死，只剩「第四份源 + 接线 + 人工验证」。

## 3. 与 A1（Vulkan）的共享边界

| 资产 | 能否复用 | 说明 |
|---|---|---|
| SPIR-V 发射器（`vulkan/spirv_rt.rs`） | ❌ 不复用 | WGSL 是文本，无「文本→文本」规范；与 MSL 同定案走手写双份源 |
| 算法与求值树（逐式对应 CPU 参考） | ✅ 直接复用 | 这是**跨后端唯一权威**：`CpuRefBackend::render_scene` |
| 槽位布局（球/灯各 8 槽） | ✅ 直接复用 | 扁平 `array<f32>`，无对齐陷阱 |
| 参数位型传参（f32 位型 + u32 标志） | ✅ 直接复用 | WGSL `bitcast<f32>` |
| 两层判据（双跑逐位 + 跨后端统计） | ✅ 直接复用 | 判据本身与后端无关，只有「能自动化到什么程度」不同 |
| `NoContraction` 装饰 | ❌ 无对应物 | WGSL 无该装饰；是否允许收缩需实测（见 §4 风险 R2） |
| lavapipe 实测数值（0/0 逐字节） | ⚠️ 仅作参考 | 那是 llvmpipe 的浮点行为，不代表浏览器 GPU 行为 |

**共享边界一句话**：**算法与判据层完全共享；源码层是三份手写（WGSL / MSL / SPIR-V 发射器）；
验证层 Vulkan 可自动化、WebGPU 不能。**

## 4. lavapipe 经验能否迁移（逐条）

| 经验 | 可否迁移 | 理由与建议 |
|---|---|---|
| 「同式发射 + 禁收缩 + 无超越函数」三纪律 | ✅ 意图可迁移 | 前两条在 WGSL 变成「不写 `fma()`、不重排表达式」；第三条同（D-29 禁 libm） |
| 逐位对拍可达（llvmpipe 上 0 差异） | ⚠️ 不可假定 | 浏览器 GPU 的除法/开方精度、denormal 处理由驱动决定；**必须在目标设备实测后才能定阈值** |
| 槽位 ABI 的「编码器 + 单测钉偏移」方法学 | ✅ 直接照搬 | 已在 `metal/render.rs` 用过；WGSL 侧同样可做（native 单测钉 `array<f32>` 的索引约定） |
| 参数以位型传入（无十进制往返） | ✅ 直接照搬 | 消除第二套舍入口径 |
| 结构校验先于真机（`spirv::validate`、`check_control_flow`） | 🟡 部分 | WGSL 没有等价二进制校验；只能做文本级结构自检（`shaders.rs` 已有） |
| 「无设备 ⇒ 静默回退 CPU」 | ✅ 直接照搬 | `WebGpuBackend::render_scene` 已是这个形态 |
| 可用性双自检（compute ∧ render） | ✅ 建议照搬 | 与 Vulkan A1 同一语义：`is_available()` 必须蕴含「能出图」 |

**关键结论**：lavapipe 经验里**可迁移的是「方法」**（怎么证明对、怎么摆放 ABI、
怎么守诚实边界），**不可迁移的是「数值」**（0 差异是 llvmpipe 的运气，不是定理）。

## 5. 风险表

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **验证链不可自动化**：CI 无浏览器 GPU，只能人工跑 | 「真跑」退化成「声明」 | 沿用 D-14 harness + 真机留档；测试项在 native 下如实 `Skip`（不假绿） |
| R2 | **浮点收缩/精度不承诺**：WGSL 无 `NoContraction`，驱动可能融合 `a*b+c` | 与 CPU 参考的末位置移 | 代码不写 `fma()`；阈值按实测（先 16/255，实测后收窄，同 A1 流程） |
| R3 | **denormal 刷新**：部分 GPU 把 denormal 刷成 0 | 极端暗部像素偏差 | 场景亮度远离 denormal 区；必要时在 CPU 侧把输入钳到正常数域 |
| R4 | **浏览器碎片化**：Safari/Firefox 的 WebGPU 成熟度不一 | 「跑通」只在部分浏览器成立 | 明确支持矩阵（Chrome/Edge 优先），`AdapterSummary` 记录 adapter |
| R5 | **与既有 scan/sort 链路争用 ABI** | 新增测试项可能扰动既有测试项清单 | 追加式新增，不改既有项；native 桩同口径 |
| R6 | **范围蔓延**：一旦接线就想顺手做后处理/多 pass | 天级变周级 | 严格限定「单 compute kernel 出 RGBA8」；其余留名（见 `docs/v2.1-longtail-inventory.md`） |

## 6. §10.3 岔路决策建议：自研补完 vs 换 wgpu

> 岔路原文见 `docs/设计/研究/能力对齐的数学分层.md:509-510`、`:598`
> （「自研补完 vs wgpu，是工程判断，不占研究线」）。

**建议：继续自研补完，不引 wgpu。**

理由（按权重排序）：

1. **零依赖宪章是硬约束，不是偏好**。`wgpu` 会拉进上百个传递依赖（`naga`、
   `raw-window-handle`、`ash`/`metal` 绑定等），与 PRD G2「`Cargo.lock` 零新增
   外部 crate」直接冲突；而本项收益仅「省 4–6 人日」。
2. **确定性承诺会被稀释**。自研路径能保证「同一 kernel 源、同一判据、同一
   量化口径」在三个后端上逐式对应；`wgpu` 会把 shader 编译（WGSL→SPIR-V/HLSL/MSL）
   交给第三方，末位行为不再可解释——而这正是 A1 花一整轮才拿到的能力。
3. **沉没成本已经变成资产**：Vulkan 侧 19.5k 行（含发射器、结构校验、探测链、
   双自检、真机对拍）全部可解释、可修改；换 wgpu 等于把这些重新外包出去，
   且**无法复用**已证明的对拍链路。
4. **增量成本不对等**：WebGPU 渲染只差「第 4 份 kernel 源 + 一条 bind group +
   人工验证」，而换 wgpu 是「推倒三后端 + 重做判据 + 重新证明确定性」。

**触发重估的明确判据**（任一成立即应重新评估，而非凭感觉）：

* 需要 **≥3 个新的图形管线特性**（如真正的 render pass/深度/多重采样/后处理链），
  自研成本超过 2 周；
* 需要支持 **Vulkan/Metal/DX12 全平台窗口表面 + swapchain**（自研要重写呈现层）；
* 零依赖宪章被作者显式放宽（那就不再是"自研 vs wgpu"的工程问题）。

## 7. 若 V2.2 立项：建议排期与验收判据

**任务拆解（4–6 人日）**

| 序 | 任务 | 产出 | 人日 |
|---|---|---|---|
| 1 | `shaders/scene_frame.wgsl`（手写，入口 `scene_main`） | 第四份 kernel 源 | 1–2 |
| 2 | `web/device.rs` 的 `render_scene` 真实路径 + 4 绑定接线 | 出图代码 | 1 |
| 3 | `web/abi.rs` 新增 1 个场景渲染测试项（run/collect） | 对拍入口 | 0.5 |
| 4 | 真机验证（Chrome/Edge，至少 2 台设备）+ 留档 | 实测数据 | 1–2（人工） |

**验收判据（与 A1 对齐，不另立口径）**

1. 有 `navigator.gpu` ⇒ `render_scene` 返回 `w*h*4` 有效帧；否则回退 CPU（不假帧）。
2. **同设备双跑逐字节一致**（硬判据，G3）。
3. 与 `CpuRefBackend` 统计对拍（阈值按实测收窄，同 Q1 流程），并显式声明
   「不经 ACES 链路」（R2 口径）。
4. `is_available()` = **compute 自检 ∧ 渲染自检**（与 Vulkan Q4 收口同语义）。
5. native 下不 panic、不假绿（`Skip` 而非 `pass`），`qa_ignore_guard` 零命中。
