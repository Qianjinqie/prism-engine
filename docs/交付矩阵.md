# Prism 交付矩阵（V2.0-K）

五个交付形态 × 三个维度（**能力 / 确定性 / 体积**）的对照表。

> **口径声明（先读这段，避免误读数字）**
>
> - 本表所有体积数字来自**同一内容**：`prism-mux::video::gen_test_frames(320, 180, 48)`
>   —— 渐变背景 + 一个 200×150 纯色块每帧右移 4 px，**320×180 @ 24 fps × 48 帧**（2 秒），
>   源数据 RGBA8 共 11,059,200 B。
> - **PRMV / MJPEG / EXR-seq 三列为本仓实测**（命令见文末「复现」）；
>   **H.264 / HEVC 两列由本机 ffmpeg（N-124111）实测**，但编码器是 `libopenh264` /
>   `libkvazaar`（本机无 libx264/libx265），**且输出为 yuv420p（4:2:0 色度下采样）**，
>   而 PRMV/MJPEG 是 4:4:4 全色度。**这是量级对照，不是 BD-rate 结论**。
> - 跨编码器的 PSNR **不可直接比较**（PRMV/MJPEG 的 PSNR 在 RGB 三通道上算，
>   ffmpeg 的在 yuv420p 上算），故 PSNR 只作为"该体积对应的画质档位"参考，标注了各自口径。
> - 合成序列（大面积平滑渐变 + 单一平移色块）对**任何**编码器都偏有利；真实实拍/复杂
>   渲染序列上各列的体积都会显著上升，**相对排序不会因此反转**（H.264/HEVC 的优势只会更大）。

## 一、总表

| 维度 | **PRMV**（本仓时序容器） | H.264（ffmpeg / libopenh264） | HEVC（ffmpeg / libkvazaar） | **MJPEG**（本仓 `write_mp4_jpeg_color`） | **EXR-seq**（本仓 `exr_seq`） |
|---|---|---|---|---|---|
| **能力** | I/P 帧间预测（IPPP，无 B 帧）；16×16 整块运动搜索 + **qpel（1/4 像素）双线性运动补偿**；Y/Cb/Cr **三平面独立灰度 JPEG 残差**（不做颜色变换、不下采样，故无交叉串色）；GOP 级率控（依赖加权 water-filling + 一阶质量控制器）；MV 表 zlib 压缩；**私有容器 `PRMV` v3，仅 prism 可解** | 完整标准：CABAC、B 帧、多参考、去块滤波、CRF/2-pass/ABR、软硬件解码器生态全覆盖；支持任意播放器/剪辑软件 | 完整标准：CTU 64×64、SAO、10bit/HDR 通道、比 H.264 再省 ~30–50%；生态同上 | **帧内 only**（每帧一张完整 JPEG，4:4:4），无任何帧间预测；**任意单帧可独立解码/截取**；容器为私有 `PRMV` | **无损浮点**（4 通道 `R/G/B/A` Float，值域 [0,1]，逐通道精确往返）；**逐帧完全独立**（无预测、无跨帧依赖）；任意后期工具（Nuke/Resolve/AE）直读；支持 10 种 OpenEXR 压缩 |
| **确定性** | **强确定**：全链路整数运算（DCT/IDCT 定点、双线性插值定点、率控只走 `det_log2/det_exp2`），**零 libm、零线程、零时间戳**；同输入两跑**逐字节相同** | **非确定**：默认多线程 + `libavcodec` 版本/指令集相关的码率控制与 RD 决策；`-threads 1` 只能做到"同版本可复现"，**跨版本/跨平台不保证同字节** | 同 H.264（且 `libkvazaar` 默认 `--owf=auto` 多线程波前并行，跨机器体积会漂） | **强确定**：自研 JPEG 编码器（整数 DCT + 固定量化/Huffman 表），同输入逐字节相同 | **强确定**：属性顺序固定、通道序固定 `R,G,B,A`、deflate 为定序 LZ77 + 固定 Huffman；同输入逐字节相同。**注意**：与官方 OpenEXR 写出的字节**不同**（仅互相可读，不是同字节） |
| **体积**<br>（48 帧合计） | **239,089 B**<br>≈ 4,981 B/帧 · **0.692 bpp**<br>参考画质 41.65 dB（RGB） | **12,808 B**<br>≈ 267 B/帧 · **0.037 bpp**<br>ffmpeg 报 36.09 dB（yuv420p） | **9,419 B**<br>≈ 196 B/帧 · **0.027 bpp**<br>（本机 PSNR 口径不可比，未列） | **316,480 B**<br>≈ 6,593 B/帧 · **0.916 bpp**<br>（q=85，4:4:4） | **1,846,752 B**（Zip）<br>= **38,474 B/帧**；未压缩档 **924,811 B/帧**<br>≈ 44.9 MB（Zip）/ 44.4 MB（None）级 |

## 三、体积列的边界与已知短板（不粉饰）

1. **PRMV 比 H.264 大 ~19 倍**。原因清楚且不神秘：
   - 残差用**三张独立灰度 JPEG**（4:4:4）编码，而 H.264 用 4:2:0 + CABAC + 变换量化联合优化；
   - MV **无预测、无算术编码**（只做整表 zlib），H.264 的 MV 用中值预测 + CABAC；
   - 无去块滤波、无 RD 优化、无 B 帧。
   
   本仓上限目标不是"打赢 H.264"，而是**在不引入第三方依赖的前提下，提供确定性可复现的自有时序码流**——这正是回归测试要的（同输入同字节，可逐字节断言）。
2. **MJPEG 比 PRMV 大 32%**：证明帧间预测 + qpel 确实在起作用（同参数 q=85、同内容，
   PRMV 239,089 B vs MJPEG 316,480 B）。注：整像素基线（`subpel = false`）在这条 48 帧
   平移序列上的同口径体积本轮未单独测（该序列运动恰为整数像素，qpel 与基线的体积差异
   应很小），故本表不引用该比值；qpel 的收益在**亚像素**内容上量化，见 §五
   （−21.6% 体积、+2.577 dB）。
3. **EXR-seq 的体积是"另一种东西"**：48 帧 44 MB 是**无损浮点**的代价，不与有损编码比体积；它的价值是"逐通道精确 + 可后期"。Zip 档 38 KB/帧是**合成帧**的乐观值（大面积平滑），真拍/复杂渲染通常在原始体积的 30–60%（即 0.28–0.55 MB/帧 @ 320×180）。
4. **ffmpeg 两列的编码器不是主流选择**：本机无 libx264/libx265，只有 `libopenh264`（CBR 型）与 `libkvazaar`（需尺寸 8 对齐，已用 320×184 pad）。换成 libx264 `-crf 23` 后同内容体积通常再降 20–40%，**结论方向不变**（H.264/HEVC 仍远小于 PRMV）。

## 四、PRMV 容器版本（交付契约的一部分）

`PRMV` 的字节语义随 V2.0-K 变化，按 C13 纪律 **bump 版本而非原地改语义**：

| 版本 | 头部（宽/高/fps） | 每宏块 MV | MV 单位 | 写端 | 读端 |
|---|---|---|---|---|---|
| v1 | `u16` ×3 + `u16` gop | 2 B（`i8`×2，未压缩） | 整像素 | 不再产出 | ✅ 可读（MV ×4 → qpel） |
| v2 | `u32` ×3 + `u16` gop | 2 B（`i8`×2，未压缩） | 整像素 | 不再产出 | ✅ 可读（MV ×4 → qpel） |
| **v3** | `u32` ×3 + `u16` gop | **zlib 压缩的 `i16`×2 序列**（`[u32 count][u32 packed_len][zlib]`） | **qpel（1/4 像素）** | ✅ 唯一产出 | ✅ |

迁移等价性：`sample_plane_qpel` 在整像素位置（`fx == fy == 0`）**逐位退化为原取样**，
故 v1/v2 容器按 ×4 换算 MV 后，解码路径与旧版**数学等价**（`i16` 范围 ±8191 qpel ≈ ±2047 px，
远宽于旧的 ±127 px）。旧容器在**强亚像素**内容上画质明显低于 v3（实测 30.6 dB vs 39.4 dB）——
这正是不升级就吃不到 qpel 收益的量化证据。

## 五、本轮 qpel 对体积/画质的影响（交付依据）

同内容、同参数（gop=12、q=85、search_radius=16），仅 `VideoConfig::subpel` 不同：

| 配置 | 体积 | 每帧 | PSNR（RGB，高频"蛋托"亚像素序列 192×112×24fps） |
|---|---|---|---|
| `subpel = false`（整像素基线，= V2.0-J 行为） | 156,625 B | 6,526 B | **36.235 dB** |
| `subpel = true`（qpel） | 122,819 B | 5,117 B | **38.812 dB** |
| 变化 | **−21.6%** | | **+2.577 dB** |

同时在**整像素运动**的平移序列（§一 那 48 帧）上 qpel 也不劣化：体积 239,089 B（0.692 bpp），
PSNR 41.65 dB，且比 MJPEG 小 24.5%。

## 六、复现

```bash
# 1) 本仓实测（PRMV / MJPEG / qpel 对照 / EXR 序列）
cargo test -p prism-mux  --lib -- --nocapture video_roundtrip_psnr   # [volume] 行
cargo test -p prism-mux  --lib -- --nocapture qpel_psnr_not_worse    # [qpel-psnr] / [qpel-size]
cargo test -p prism-render --lib -- --nocapture exr_sequence_volume  # [exr-volume] 行

# 2) ffmpeg 对照（H.264 / HEVC）
#    先把 gen_test_frames(320,180,48) 的 RGBA8 原始帧导出为 pan.rgba（每帧 w*h*4 字节）
ffmpeg -f rawvideo -pix_fmt rgba -s 320x180 -r 24 -i pan.rgba \
       -c:v libopenh264 -b:v 500k -g 12 -pix_fmt yuv420p -f h264   h264.raw   # 12,808 B
ffmpeg -f rawvideo -pix_fmt rgba -s 320x180 -r 24 -i pan.rgba \
       -vf "pad=320:184:0:0,format=yuv420p" \
       -c:v libkvazaar -b:v 300k -g 12 -f hevc                     hevc.raw   # 9,419 B
ffmpeg -f rawvideo -pix_fmt rgba -s 320x180 -r 24 -i pan.rgba \
       -c:v mjpeg -q:v 4 -pix_fmt yuvj420p -f mjpeg                mjpeg.raw  # 110,299 B（参考）
```

本机环境：`ffmpeg version N-124111-g9e90fa505e`，Linux x86-64，无 libx264/libx265。
