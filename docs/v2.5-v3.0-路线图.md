# V2.5–V3.0 路线图：最后一次能力对齐，然后回到本心

> 作者：齐活林（交付总监）｜ 定稿依据：引擎作者 2026-11-01 拍板 ｜ 状态：待评审
>
> **事实基线**：29 crate、**4029 passed / 0 failed / 188 测试段**、wasm **453,239 B**、
> WebGPU 真机 4 环境 × 2 设备 **各 19/19**。

## 0. 版本定位（作者拍板原话）

| 版本 | 定位 | 一句话 |
|---|---|---|
| **V2.5** | **最后一次能力对齐**——真正不输于其他商业闭源引擎。**仅无硬件的情况可以赦免** | 把"能不能做"这个问题结清，之后不再回答 |
| **V3.0** | 能力已补齐，回到引擎本心——**视频即代码工程**：一段代码转化为一段视频 | 把"怎么做"这个问题做成产品 |

两级的关系是**串行**，不是并行：V2.5 没结清，V3.0 不启动。理由——V3.0 的语言要能触达引擎全部能力，能力边界未定则语言规格无法封闭。

## 1. 判定规则（先定规则，再谈内容）

### 1.1 五态制

| 状态 | 定义 | 是否阻塞 V2.5 出口 |
|---|---|---|
| **已对齐** | 有实现 **且** 有 golden 判据 **且** 有对拍证据（真机或参考实现） | 否 |
| **部分** | 有实现，但有明确缺口（写在备注列） | **是**（P0 项） |
| **未点亮** | 无该平台/硬件可验证，显式登记，不写"支持" | 否（豁免） |
| **不验（裁定）** | 有硬件可验，但判定证据已充分，明确不做；须写裁定理由 + 重开条件 | 否（裁定） |
| **缺失** | 没有实现，或实现但无判据 | **是**（P0 项） |

**出口判据**：P0 列只允许出现「已对齐」「未点亮」「不验（裁定）」。出现「部分」或「缺失」即 No-Go。

### 1.2 不计分项（作者 2026-11-01 拍板）

> "说的是能力对齐，看引擎能力，至于输出个什么格式不太重要。"

因此以下项**不进能力矩阵、不参与 V2.5 评分**，归**交付层**：

- 输出容器与编码格式（PRMV / MJPEG / EXR-seq / MP4）
- 码流体积（PRMV 0.692 bpp vs H.264 0.037 bpp 的 19× 差距，**不算能力缺口**）
- 第三方播放器/剪辑软件的兼容性

> 硬件编码**不在**此列——它是平台能力项，已在 §2.4 P-5 登记为「未点亮」。

**连带结论**：零第三方依赖红线**不松绑**。`Cargo.toml` / `Cargo.lock` 维持全 path 依赖。
若将来客户需要 MP4 母版，做法是**交付层可选桥**（P2，独立 crate + feature gate，不进默认依赖树），不是能力项。

### 1.3 「未点亮」的成立条件（三条同时满足，缺一不成立）

作者原话：

> "比如说像 iOS/macOS 的后端，团队没有设备，无法验证，直接实现肯定会有 bug 存在，那还不如说直接说明未点亮。"

落成制度：

1. **写明缺什么**：缺的是设备、样本还是操作系统，具体到型号级别（例："无 Apple Silicon 设备"）。
2. **同步标注**：README、能力矩阵、Release note 三处一律写「未点亮」，**任何一处不得写"支持"**。
3. **写复验触发条件**：什么条件下重新验证（例："取得任意 M 系列设备即复验 Metal 后端 19 项"）。

**未点亮不是"可以不写代码"的许可证**——恰恰相反：不写代码可以标未点亮，写了但没验过的代码**不允许**标"已对齐"。半成品冒充已支持，是比未点亮严重得多的问题。

### 1.4 反假绿条款

沿用 V2.2 已立的口径：**"两端同错"的自洽对拍不构成能力证据**。凡判据建立在"CPU 参考 vs GPU 镜像"上的项，至少需要一条独立证据（真机、第三方参考实现、或解析解）。

| P-6 | ARM Mali / PowerVR | 未点亮 | 无设备；现有覆盖仅 Qualcomm Adreno 640/619 两代 |

> **P-3 为什么可以不做桌面验证（作者裁定，2026-11-01）**
>
> 真机暴露过的缺陷只有两类：
> ① **逻辑类**（球 SDF 返回 `q.x`、折射法线未翻转）——与后端无关，软件适配器就能捕获；
> ② **后端类**——只有 `vec3<f32>` 存储布局一例。
>
> 而第 ② 类已经被**结构性消掉**，不是靠概率赌：V2.2 把四个布局结构体全部改 `vec4<f32>`（`GI_*_STRIDE_BYTES`
> 一格未动），并加了「存储布局禁 `array<vec3<f32>>`」的静态门禁。桌面后端最可能暴露的那一类风险，
> 现在连写都写不出来。
>
> **重开条件（任一触发，P-3 立即恢复为 P0 验证项）**：
> ① 有用户报告桌面端渲染差异（需附 `adapter` 与浏览器版本）；
> ② 改动任何布局结构体（`GI_*_STRIDE_BYTES` 或场景 ABI 结构）；
> ③ 新增依赖驱动扩展/精度的能力（如 subgroup 运算、16 位存储纹理）。
>
> **成本前提**：本裁定以「不为此专门添置桌面设备」为前提。README 现写「桌面实跑一次即可结项（约 5 分钟）」——
> 若手边本就有可用桌面，这句话成立，顺带跑一次即可；若要为此买机器，则不值。
>
> **同时约束**：不验就不许暗示支持。README / Release 一律写「移动端已验（4 环境 × 2 设备）；
> 桌面未验证」，不得只写「支持 Chrome/Edge」。

## 4. V2.5 里程碑

不排工期数字，按波次推进。**硬约束：每一波最多容纳一个结构级改动**（改 `Scene` / `Bsdf` / 三后端 ABI 的算结构级），避免两个重构撞在同一波里各自改坏对方的基线。任一出口判据未达即重评，不进入下一波。

| 里程碑 | 目标 | 需求 | 依赖 | 出口判据 |
|---|---|---|---|---|
| **V2.5-M1 着色对齐** | 纹理与光照补齐——这是观感差距的主因 | A1、A2 | 无（M1 是后续地基） | ①**纹理正确性**：双线性在纹素中心精确命中（无半像素偏移）；mip 使斜视平面与 64× 超采样参考图差异 ≤ 2/255；uv 缝无接缝。②**IBL 白炉**：常数环境 + 完美白漫反射 → 输出等于环境辐亮度（误差 ≤ 1%，解析解，非自比）；环境中置已知方向亮斑，镜面反射方向命中该亮斑。③三后端（CPU/Vulkan/WebGPU）同场景 `differing_pixels = 0` |

### 4.1 算法选型原则（先选算法，再定结构）

作者 2026-11-01 定：**对齐只是不输，赢要靠算法。** 工程师动手前先做算法选型，结构为算法服务；**禁止照着商业引擎的功能清单逐项复刻**。

#### 已有的算法底子（不需要重做）

| 已有 | 位置 |
|---|---|
| Sobol 低差异序列 + PCG 派生 | `sampler.rs`、`web/abi.rs:4028` |
| SAH BVH，且构建确定性 | `geometry/bvh.rs:642`、测试 `sah_build_is_deterministic` |
| NEE + MIS | `rt/light.rs:106` `nee_mis_weight` |
| MNEE 焦散（镜像/折射） | `rt/caustics.rs:164` |
| à-trous 空域 + 确定性时域累积 + 方差引导 | `postfx/denoise.rs` |
| SVGF 两阶段 | `denoise.rs:239` |

**这些已在商业引擎的水平线上，不是差距所在。** 差距只在"有没有"——纹理、IBL、实例化、细分、毛发、多区域介质，全是**能力缺口，不是算法缺口**。

#### "赢"的机会：补缺时跳过商业引擎的历史包袱

商业引擎的很多做法，是为"实时 / 每像素单样本 / 老硬件"妥协出来的。本引擎是**离线、多样本、全链路确定性**，可以直接采用那些在实时场景里根本不可行的方案。

| 缺口 | 商业引擎常规做法（带包袱） | 本引擎可直接采用（更省且更好） |
|---|---|---|
| A1 纹理 | mip 链 + 三线性 + **各向异性足迹计算**（整条管线最难的一块） | **随机纹理采样**：每样本随机 mip 级，靠多 spp 累积自动得到正确滤波。省掉各向异性足迹，且**无过度模糊** |
| A2 IBL | 预过滤 cubemap + split-sum 近似（有能量损失、漏光） | **直接对 HDR 环境图做 CDF 重要性采样 + MIS**：无预过滤、无近似，能量精确 |
| A5 自适应 | 反馈式迭代（非确定，两跑不一致） | **利用 Sobol 序列的渐进性**：前 N 点仍是低差异，"用多少算多少"，天然确定性，**不需要反馈回路** |

> 上表是**候选方向，不是定稿**。W0 须由工程师逐项验证并出选型报告——预期收益、实现量、与确定性基线的兼容性，三条都要有数字或可证依据。**不许写"应该更好"。**

#### 算法不是圣旨（作者 2026-11-01 定）

选型报告是**可被推翻的方案，不是必须执行的规格**。

实现工程师在动手时若发现算法有错——假设不成立、边界情况没覆盖、与确定性基线冲突、实测收益不如预期——**应当直接改算法并记录原因**，不许"照错的算法实现完再说"。监督和执行分离在这里不成立：只有真正在写那几百行的人，才知道假设在哪一步塌了。

**错误留在算法里，代价会随波次放大**：W1 选错，W2–W7 全建在上面；等到 W7 真机才发现，改的不是算法，是地基。

改算法时的两条纪律：

1. **必须记录**：改了什么、为什么、实测数据是什么。写进 `CHANGELOG.md` 对应条目，不写口头说明。
2. **若改了结构**：凡涉及 ABI 字段的，必须回到 W0 重新定桩并重新跑断言，**不许在实现里偷偷加字段**——这是 `vec3<f32>` 事故的同款路径。

#### 验证与设计不分家

不另设"专职验证"环节。选型的人自己给验证方法与数据：候选方案的收益怎么测、测什么指标、预期落在哪个区间。**报告里没有验证路径的方案，等同于没做选型。**

#### 超越判据（V2.5 出口新增）

除 §4.5 五条外，P0 项中**至少 2 项**须给出"相对商业引擎默认做法的可测量优势"，并附对拍数据。例：同 PSNR 下样本数更少 / 无预过滤误差 / 同质量下内存更小 / 无过度模糊（高频细节保留率）。

**只对齐不算完成。** 两项而非一项，是因为单项可能是运气——两项才能说明选型方法本身有效。

### 4.3 验证分层（真机只在收口跑一次）

真机不做常规验证。风险分四类，各有各的手段。**注意第三类与第四类性质不同**：前者是我们的错，后者不是我们的错，但两者在产品里造成的后果一样。

| 抓什么 | 手段 | 什么时候 | 责任归属 |
|---|---|---|---|
| **逻辑错误**——采样写错、权重算错、BVH 节点错位 | SwiftShader 软件适配器跑 19 项 harness | **每波结束** | 我们 |
| **我们的布局错**——字段偏移算错、对齐算错、类型选错（规范内可判定） | `scene_abi.rs` 单一权威 + `size_of`/`align_of` 编译期断言 + 禁 `array<vec3<f32>>` 静态门禁 | **编译期**，写错就编不过 | 我们 |
| **驱动实现偏差**——同一条规范，某厂商不这么实现（`vec3<f32>` 那次即此类） | 保守类型策略缩小暴露面（W0 定）+ 真机兜底 | 真机 **仅 W7** | **驱动实现方** |
| **后端实现差异**——精度、subgroup 行为、扩展支持 | 真机（2 台 Adreno + 多浏览器） | 真机 **仅 W7** | 平台/硬件 |

**责任划分（作者 2026-11-01 裁定）**：若代码在规范内、软件适配器按规范通过、真机因**驱动不规范**而失败，**缺陷责任在驱动实现方，不计入引擎缺陷**。

但这不豁免两件事：

1. 必须把该写法登记为「已知不兼容」，并给出规避写法——不是修完就算，是**写进文档让下次不再踩**；
2. 不得据此关闭问题单。沿用 §9.5 责任边界条款：免责需三条同时成立（输出可证符合规范 / 规范实现上通过 / 已尽合理规避），且**不得以"符合规范"当作"不用测"的理由**。

**所以保守类型策略的真实作用，不是防我们写错，而是缩小与不规范驱动打交道的表面积。** 新增字段只用 `vec4` / `f32` / `u32`，不是因为这些类型"更对"，而是因为它们在各家驱动上的实现分歧最小。这是唯一能在事前做的那部分——驱动内部怎么实现，我们改不了。

**为什么布局不能靠软件适配器兜**：SwiftShader 是**严格按规范实现**的（`host_test.mjs:775` 已有注释记录它会按规范把越界的 `samples[6]` 压到 `sh[0]`），因此"符合规范、但某个真实驱动不这么干"的差异它天然抓不到。V2.2 的 `vec3<f32>` 就是这样漏到真机的。

**本方案成立的前提**：把「属于我们的那部分」布局风险从运行时挪到编译期。否则 W1–W6 全绿、W7 真机一挂，六波累积的改动无从二分——即便事后能证明责任在驱动，**返工的成本仍然由我们承担**。责任归属与损失归属，不是一回事。

**真机失败时的定位路径**（按作者裁定，单独打 bug）：

1. 查断言与门禁是否被绕过 → 布局类；
2. 跑 `host_test.mjs` 的 12 组 CPU/GPU 对拍 → 算法类；
3. 仍存疑则按波次 tag 二分回滚（每波可停，天然是二分点）→ 波次引入类。

### 4.4 两条跨波红线

1. **预览不得另起近似路径。** W7 的预览必须是同一渲染器的低 spp / 低分辨率档。若另写一套"快速着色器"，引擎里就有了两个事实源——预览看着对、出片不对，这是最难查的一类 bug。因此 W6 的 tile 调度与 W7 的增量渲染**共用同一套调度器**，设计时一起谈、实现时分波。
2. **每一波结束都必须可停。** 出口判据未达不许进入下一波；但已通过的波次必须能独立停在绿色状态——不留"半截 ABI"或"只改了一个后端"的中间态。

## 5. V3.0 作者契约

### 5.1 形态：单文件（作者 2026-11-01 拍板 A）

> 一部片子 = **一个文件**。场景、时间线、材质、资产引用、渲染设置全在里面。
> 一条命令出片，改哪句改哪句，整片重出，每次结果一模一样。

类比：LaTeX 的 `.tex` → PDF。**不做工程目录**（B 案）**也不做纯 SDK**（C 案）——两者都可作为"导出/嵌入"形态存在，但不是作者契约的主形态。

### 5.2 语法：Python 级可读性，能力不打折（作者拍板）

> "语法就设个像 Python 一样好读，同时能力也不缺。"

这句话拆成两条硬约束：

| 约束 | 含义 | 反例（不做） |
|---|---|---|
| **好读** | 缩进块、`def` 函数、表达式、列表/字典字面量、字符串插值、`for`/`if`；报错带行号 + 人话建议 | 现有块语法（`scene "x" { sphere ball { radius 1.0 } }`）能声明但不能计算 |
| **不缺** | 语言必须能触达 §2 矩阵的**每一项**能力，不是"简化版 API" | 只暴露 20% 参数的"易用封装" |

**语义是确定性受限子集**——这是与 Python 的关键差异，必须写进语言规格：

- 无系统时间、无网络、无文件写、无环境变量读取；
- 随机必须显式播种（种子进产物哈希）；
- 浮点须走确定性口径：固定求值顺序 + 引擎 `det_*` 超越函数，**不依赖平台 libm 差异**（须逐函数确认，超出 `det_*` 覆盖面的函数要补实现）；
- 无隐式全局状态；同文件同种子两跑逐字节一致。

### 5.3 与现有 DSL 的关系

不是推倒重来，但也**不是只加语法**。现状（`docs/v2-节点覆盖盘点.md` §1）：

- DSL v2 有 **8 类可建节点写法**，`render_movie` 只支持 **4 类**（camera / material / sdf / text）；
- `particles` / `sim` / `compose` 明确报 **R5010**（缺粒子域求值器、缺 XPBD 步进、输入不可达）；
- `layer morph` 与 `light` 节点未进 render 面。

即：**语法够用一半，求值覆盖面还差一半**。而引擎侧这两块能力其实是有的——`prism-particles`（1.6k 行）、`prism-physics`（11.3k 行）。缺的是"从 DSL 到求值器"的那一段接线。

因此 V3.0 是两件事并行：

| 线 | 内容 |
|---|---|
| **A · 语法升级** | 表达式与变量（`d = 3.0`、`radius = d / 2`）、函数（`def orbit(center, r):`）、控制流（`for i in range(12):` / `if`）、单文件资产引用、统一顶层入口 |
| **B · 求值补齐** | particles / sim / compose / morph 接进 DSL 求值链，R5010 全部销号 |

现有块结构（`scene "x" { … }`）**保留为语法糖**，不删除——它是黄金测试的零损失凭证（`examples/spin_red_ball.prism`）。

### 5.4 V3.0 出口判据

| # | 判据 | 验证方式 |
|---|---|---|
| 1 | 一部 3 分钟片子 = 一个文件 | 仓库内 `examples/films/*.prism` 各一个文件，无外部依赖目录 |

## 6. 决策点

| # | 决策 | 结论 | 日期 |
|---|---|---|---|
| **D-7** | V2.5 比什么 | **比引擎能力，不比输出格式**。容器/编码/体积/兼容性归交付层，不计分 | 2026-11-01 已定案 |
| **D-8** | V2.5 判定口径 | **分域能力矩阵**，五态制（已对齐 / 部分 / 未点亮 / 不验·裁定 / 缺失），P0 列不得出现「部分」或「缺失」 | 2026-11-01 已定案 |
| **D-9** | 无硬件怎么办 | **显式「未点亮」**，不写半成品冒充已支持；须写明缺什么 + 复验触发条件 | 2026-11-01 已定案 |
| **D-10** | V3.0 作者契约 | **单文件 + Python 级语法 + 能力不打折** | 2026-11-01 已定案 |
| **D-11** | 零依赖红线 | **不松绑**（D-7 的直接推论：格式不计分，无需为兼容性引依赖） | 2026-11-01 已定案 |
| **D-12** | V3.0 语法实现路径 | 倾向**自研解析器**（零依赖，不嵌 Python、不引 `pest`/`nom`）；需评估手写 LL 与错误恢复成本 | **待作者拍板** |
| **D-13** | 细分曲面口径 | Catmull-Clark 自研 vs 只支持 Loop/线性细分 | 待定 |
| **D-14** | IBL 采样结构 | 等距柱状 + 2D CDF vs 立方图 + 分层 | 待定 |
| **D-15** | V2.5 是否包含实时预览 | **包含**。B3 升 P0、进 M4；预览必须是同一渲染器的低质量档，不另起近似路径 | 2026-11-01 已定案 |
| **D-16** | 桌面 WebGPU 是否单列验证 | **不单列**。软件适配器 + 移动端已足证正确性；V2.2 的 `vec3`→`vec4` 改造 + 静态门禁已结构性地消掉桌面最可能暴露的那类风险。附三条重开条件，且对外不得暗示桌面已支持 | 2026-11-01 已定案 |
| **D-17** | 波次的验证手段 | **软件适配器（SwiftShader）跑每波，真机只在 W7 收口跑一次**；真机失败单独打 bug。前提是**属于我们的**布局风险已前移到编译期；驱动偏差无法前移，只能靠保守写法缩小暴露面 + W7 兜底 | 2026-11-01 已定案（作者） |
| **D-18** | 真机因驱动不规范失败的责任归属 | **责任在驱动实现方，不计引擎缺陷**。但须①登记「已知不兼容」+ 规避写法；②不得据此关闭问题单（§9.5 三条前提仍适用）。责任归属 ≠ 损失归属，返工成本仍由我们承担 | 2026-11-01 已定案（作者） |
| **D-19** | 产品出片用哪个渲染器 | **双轨**：默认 `prism-rt`（完整路径追踪），`--fast` 走 `CpuRefBackend`；`CpuRefBackend` 同时保留为测试对拍参考。**重开条件**：prism-rt 确定性验证失败，或性能不可接受 | 2026-11-01 已定案（作者） |
| **D-20** | 是否允许按 tile 多线程 | **允许**。前提：tile 尺寸与核数无关、归约顺序固定、结果与单线程逐字节一致。纪律的目的是确定性，不是禁止并发——并发若能证明确定，就不该禁 | 2026-11-01 已定案（作者） |
| **D-21** | 「零依赖」约束的是**交付物**还是**工具链** | **只约束交付物**。判定标准：clone 后 `cargo build` 不联网、不拉 crates.io、源码内无第三方代码。开发期编译器（`tools/wgsl2spv`，naga 30.0.1）不算依赖——它不参与构建，只是把编译器当尺子用。三条硬约束防回潮：①`tools/` 被 workspace `exclude`、自带 `Cargo.lock`；②产物 `.spv` 入库，`build.rs` 不生成不调用、release 路径不经过 `tools/`；③主仓测试反查（`cargo tree` 零第三方 + `tools` 不在 members）。**静默重生成视为违规**——改了 WGSL 忘重生成必须红，否则工具会悄悄退回依赖位 | 2026-11-01 已定案（作者） |
